## Verified: real FreeInk C++ driver transactions

- UC8253 for X3: actual 792x528, 47 recorded SPI command/data operations, 3 refreshes; framebuffer check at known pixels passes.
- SSD1677 for X4: actual 800x480, 30 recorded operations, 1 refresh; BW/old planes have 48000 bytes each; expected pixel positions pass.
- Both traces are generated by executing the repository's real FreeInk C++ panel drivers against recording EpdBus, not by synthetic commands.
- Python epd_protocol.py is a command/data state machine with separate controller RAM and visible pixels. It does not execute ESP32 firmware or attach to an emulated GP-SPI bus.

## Open QEMU implementation investigation

Source: espressif/qemu commit febae18 (GPL), inspected separately from binary-only espressif/esp-emulator.

- ESP32-S3 machine (hw/xtensa/esp32s3.c) already instantiates DWCSDMMCState at DR_REG_SDMMC_BASE and attaches SD card from -drive if=sd. This may work for X4 Pro, but must be proven by actually booting YBX factory firmware with test SD media.
- ESP32-C3/S3 machines only wire SPI1 for Flash/PSRAM. Xteink EPD + X3/X4 SD SPI rely on GP-SPI2 and GPIO CS/DC/BUSY; attaching an SSI slave to the Flash bus is not a valid replacement.
- QEMU has generic SSI SD card implementation hw/sd/ssi-sd.c. Useful for X3/X4 only once GP-SPI2 and GPIO routing exist.
- Open QEMU does not automatically provide emulator Wi-Fi parity with binary esp-emu (which already has SoftAP/NAT). Functional TLS remains untested.

Build environment is pinned in `tools/ybx-system-emu/Dockerfile.qemu`.


## CPU crash analysis and first source-level fix (29 October 2026)

The initial C3 crash was in the upstream QEMU file `hw/dma/esp32c3_gdma.c`:

- Three C3 GDMA interrupt banks occupy 0x10 bytes each (offsets 0x00–0x2c); the code erroneously decoded their channels with `DMA_DIR_REGS_SIZE=0x60`, making offsets 0x10–0x2c index outside `R_DMA_INT_RAW..CLR` and assert.
- Fixed *both* interrupt-bank read and write to use `DMA_INT_CHAN_REGS_SIZE=0x10`.
- Corrected a second source defect: the conversion table has **five input and four output interrupt bits**. Dividing its odd length by two misclassified the fifth input bit. Now both mapping directions use five input entries.
- Patch is stored as `patches/0001-esp32c3-gdma-interrupt-layout.patch` in YBX; `sh tools/ybx-system-emu/apply_qemu_patches.sh` applies it only when cleanly applicable, or reports already applied, and never touches the YBX firmware.
- Verified a real incremental `ninja -j3 qemu-system-riscv32` build. **The previous GDMA assertion no longer occurs** in the actual C3 factory-image run. However, the guest now logs eFuse key/signature warnings, and QEMU reports a heap corruption on timeout/exit. It still does **not** reach a proven YBX application UART startup. Do not call the CPU boot complete in open QEMU.

S3 ROM behavior is now traced independently for CPU 0 and 1:

- Core 0 executes reset-vector instructions, ROM `boot_prepare` and later `usb_uart_device_tx_one_char`, then enters the **debug exception vector at 0x40000280** and loops at 0x40000288.
- Recorded `EXCCAUSE=0x0000000e`, `DEBUGCAUSE=0x00000008`, `EXCVADDR=0xffffffff`, `EPC1=0x40049057`. The ROM symbol for the EPC is `usb_uart_device_tx_one_char`. This suggests an invalid pointer/access in ROM UART logic; its root cause is **not yet proven**.
- Core 1 waits at ROM address 0x40043a3e for a CPU-startup handoff. That is a normal wait condition *while the first core initializes*, not itself proof of a dual-core emulation defect.
- The ROM ELF directly supplied to QEMU via `-kernel` fails on overlapping ELF program regions. Supplying only the 1,460-byte ROM DRAM initializer through generic `-device loader` also failed to load. Neither failed experiment is presented as a fix.
- The 64 MiB FAT16 card is attached to the QEMU virtual S3 SDMMC, but **no FAT mount or block I/O has been verified**.

Detailed logs, disassembly traces and JSON status are local-only:
`~/Projects/YBX/artifacts/ybx-esp32-system-emulation-20261029/qemu-cpu-blocker-20261029/report.json`.

## Root cause confirmed: missing ROM reset-copy payloads (29 October 2026)

**New reproducible finding, superseding the rejected DRAM-only experiment:**

The ESP32-S3 ROM reset routine traverses copy descriptors at
`0x40057354..0x400575c4`. These copy **from instruction ROM to DRAM**.
The original `extract_rom_elf.py` produced the instruction-ROM PT_LOAD bytes,
but the local ELF also holds initialized writable sections that must populate
the descriptor **source addresses** within instruction ROM. Consequently:

- `spi_dummy_len_fix()` at `0x400494ff` accessed an uninitialized pointer
  `rom_spiflash_legacy_data` in DRAM (`0x3fceffe4`) and raised
  `EXCCAUSE=0x1c`, `EXCVADDR=0x1b`; the ROM's
  `ets_fatal_exception_handler` then looped at `0x40050f3f`.
- ROM reset descriptor for that pointer:
  destination `0x3fceffe4..0x3fceffec`, source `0x40057874`.
  The original extracted ROM's source was zero; the local ROM ELF gives
  `0x3fcef6a4` for the first word. Other SPI Flash structures have the
  same omission (for example, source `0x40058130`).
- Pre-populating DRAM in a separate QEMU experiment was **not** effective,
  since the guest ROM reset routine overwrote it again with zero and
  `0xffffffff`. The rejected source-level trial is preserved only at
  `experiments/0004-s3-rom-initializer-trial.patch`, not in accepted patches.
- The host-only `extract_rom_with_sections.py` reconstructs the **original
  ROM reset-copy data sources** using the locally installed Espressif ROM
  ELF's writable sections. It populates 19 nonempty regions without
  altering any instruction opcodes, firmware binary, FreeInk SDK, or the
  accepted QEMU source. The separate `extract_rom_data.py` extracts the
  writable section values and validates expected SPI legacy pointers.

### USB Serial/JTAG output and actual application panic (29 October 2026)

Open QEMU's `esp32c3_jtag.c` model used by both ESP32-C3 and S3 originally
returned TX-ready (patch 0003) but discarded actual FIFO writes. The newer
`esp32c6_jtag.c` already implements the equivalent TX-byte-to-chardev
handoff. The separate verified-for-S3 patch
`patches/0005-usb-serial-jtag-output.patch` exposes a chardev for the
C3/S3 peripheral and maps it to the serial port *after* the physical UARTs
(C3 index 2, S3 index 3); normal UART0 is not replaced.

S3 build of QEMU + patches 0001, 0003, 0005 succeeded. With the corrected
ROM and `-serial null -serial null -serial null -serial stdio`, the **real**
X4 Pro firmware (SHA-256
`268c62e01ada2958fe2df0122a73dc1c037d646207805a6d14a5a6d146434b25`)
produces:

- `ESP-ROM:esp32s3-20210327`, `boot:0x4 (SPI_FLASH_BOOT)`,
  real bootloader loads from flash and `entry 0x403c8898`.
- ESP-IDF `octal_psram` / `esp_psram` reports that the PSRAM chip is
  unavailable or its bus mode is wrong. The firmware continues without it,
  then generates a **guest** `Guru Meditation Error: LoadProhibited` at
  **`PC=0x421c615e`**, `EXCVADDR=0x00000003`, and reboots.
- This is neither successful application startup nor a QEMU process abort.
  It is a real guest exception with its own backtrace, visible only after
  USB Serial/JTAG output is connected.
- Retesting with QEMU `-m 8M` (which attaches its existing virtual PSRAM
  device) produced the same PSRAM initialization errors and panic. This
  strongly suggests a missing or mismatched **Octal PSRAM protocol/mode**
  rather than solely missing configured RAM quantity.
- `run_open_qemu.py --usb-serial` now exposes this diagnostic output;
  it requires a QEMU built with patch 0005, and reports
  `guest_panic_detected` separately from `qemu_abort`.
  It refuses to claim an acceptance PASS on a timed-out or panicking guest.

Evidence: `qa-20261029/s3-usbjtag-uart.log`,
`qa-20261029/s3-psram8-usbjtag-uart.log`, and
`qa-20261029/s3-usbjtag-runner/report.json`.

### Remaining ESP32-C3 ROM blocker / S3 Octal PSRAM observation

The QEMU RISC-V target also builds with the independent USB Serial/JTAG
chardev patch 0005. A real X3/X4 C3 factory image (same `092c2be5`
revision) with `--usb-serial` exposes a ROM-level
`Guru Meditation Error: Load access fault` at
**`PC=0x4004cc4e`**, `MTVAL=0x0000001b`, `MCAUSE=0x5`;
the second-stage bootloader has not been observed. The exact matching
local Espressif C3 rev3 ROM ELF disassembles `0x4004cc4e` as
`spi_dummy_len_fix(): lbu a4,27(a5)`; the preceding instruction loads
`rom_spiflash_legacy_data` from DRAM `0x3fcdfff0`.
This is analogous to the confirmed S3 missing-reset-initializers failure,
but **no corresponding C3 ROM source-image correction has been tested yet**.
Evidence: `qa-20261029/c3-usbjtag-runner/qemu-c3.log`.

For S3, the QEMU `ssi_psram` device defaults `is_octal=false`
even when `-m 8M` attaches an 8 MiB chip. The guest's actual X4 Pro
firmware uses Octal PSRAM. The separate test command
`-m 8M -global ssi_psram.is_octal=on` was verified by QEMU
`info qtree` (device shows `is_octal=true`, `size_mbytes=8`).
With Octal enabled, the earlier explicit 'PSRAM chip not connected'
diagnostic disappears, but a 25-second no-icount run still ultimately
panics at **the same `PC=0x421c615e`, `EXCVADDR=0x3`** and
restarts repeatedly. Therefore the PSRAM mode mismatch was **not**
the sole cause, and this remains an incomplete emulator.
Evidence: `qa-20261029/s3-octal8-25s-uart.log` and
`qa-20261029/s3-octal-qtree.log`.

Symbolization of the S3 guest panic requires the **exact matching ELF**
for factory image revision `092c2be5`; other available worktree ELFs
have different SHA-256 hashes. Do **not** assign a function name to
`0x421c615e` based on a different binary. Next work should retain a
matching ELF and map file with every saved factory image, investigate
the S3 panic accurately, and separately reconstruct C3 ROM reset-copy
sources before declaring either guest boot stable.

### ESP32-C3 rev3 ROM fixed: factory application code reached (29 October 2026)

any bootloader entry. Unlike the S3 rev0 table, the C3 rev3 ROM's
32 reset-copy descriptors occupy `0x40059200..0x40059400`.
The descriptor for `rom_spiflash_legacy_data` copies **8 bytes**
from source `0x40059658` into destination `0x3fcdfff0`.
The old extracted ROM had `0x00000000` at this source, while the
matching local `esp32c3_rev3_rom.elf` has `0x3fcdf5c0`.

The new `extract_c3_rom_with_sections.py` restores **14**
nonempty reset-copy sources using writable PROGBITS payloads from
that exact Espressif ROM ELF. No instruction code is altered.
The C3 corrected ROM (local-only, never committed) has SHA-256
`5d723d466490c3295ac54068c9e90b9bc9bb5a1f03b974012b1e28a56411e511`.

`fw-092c2be5-symbols-20261029` at firmware commit `092c2be5`,
with FreeInk SDK pinned at `44427f8`. The X4 Pro PlatformIO build
`pio run -e x4pro -j 2` succeeded and generated a 100 MB debug
`firmware.elf`, under that worktree's `.pio/build/x4pro`.
The IROM segment at `0x42000020`, length **2,792,968 bytes**, of
this build and the preserved factory image are **identical**:
SHA-256 `b2116bc0fd2985d67d83ce8dbb346c41c0464a576b8aa829912a77ab4cf4e7c4`.
The factory and rebuilt IRAM segment `0x40374000` also matches
**106,644 / 106,644 bytes**. A 43-byte difference is confined
to non-executable DROM build data. The exact ELF instruction map is
therefore reliable for these IROM and IRAM crash PCs. Be aware
`xtensa-esp32s3-elf-addr2line` displays a misleading inlined
ArduinoJson template for `0x421c615e`; actual
`xtensa-esp32s3-elf-nm` plus **disassembly** demonstrates that PC
belongs to **`soc_get_available_memory_regions()`**
(beginning at `0x421c60f8`). The faulting instruction reads
`ets_rom_layout_p` from `0x3ff1fffc` then loads an additional word
via its pointer at an offset of 4. The original QEMU ROM extraction
left that DROM pointer as `0xffffffff` and the guest faulted
on address `0x00000003`.

**Shared ROM DROM fix, C3 and S3.** Both locally installed Espressif
ROM ELFs contain `.rodata.interface` sections that are **SHF_WRITE,
not ELF PT_LOAD**. QEMU aliases DROM `0x3ff00000..0x3ff20000`
to its instruction-ROM tail `0x40040000..0x40060000`.
The new `extract_rom_interface.py` validates and copies the section
to the correct ROM alias window. Both chip-specific ROM generators
invoke it *after* their reset-copy initializer reconstruction.

- C3 layout pointer `0x3ff1fffc = 0x3ff1be3c`, complete ROM
  SHA-256 `3f798154d9eccc3652ce8d38627e8716ba16b45de1b892eab55486af39ebc8fa`.
- S3 layout pointer `0x3ff1fffc = 0x3ff1ae90`, complete ROM
  SHA-256 `5b950be93a30610322a3b46049e4095cdda04f33f09fa13a9a9a6167b5994bd9`.
- The new generator outputs were **byte-for-byte verified** against
  the successful manual DROM experiments. Both corrected ROMs

### Confirmed missing I2C master mapping (remaining blocker)

Inspection of the local `espressif/qemu` source confirms that
`hw/xtensa/esp32s3.c` does not instantiate or map an
ESP32-S3 I2C master at `DR_REG_I2C_EXT_BASE=0x60013000` or
`DR_REG_I2C1_EXT_BASE=0x60027000`. Its generic catch-all
`esp32s3_io_read` returns zero for unimplemented registers.
Similarly, `hw/riscv/esp32c3.c` handles only a small RTC I2C
special case, not a compatible ESP-IDF 5 I2C master.
`hw/i2c/esp32_i2c.c` does exist for the classic
`hw/xtensa/esp32.c` machine, but is **not wired to C3/S3** and its
register semantics must be checked before adapting it. This explains
the direction of the next investigation but does not yet prove every
driver failure's exact cause. Track under Kaneo #33.

### 29 October: C3/S3 real I²C master wiring, modern opcodes and QTest

The **classic ESP32** I²C master in
`hw/i2c/esp32_i2c.c` was present but not connected to the C3/S3 machines.
The hardware registers overlap with ESP-IDF 5 C3/S3, but the command
encoding changed:

| Operation | Classic ESP32 QEMU | ESP32-C3/S3 ESP-IDF 5 |
| --- | ---: | ---: |
| RESTART | 0 | **6** |
| WRITE | 1 | 1 |
| READ | 2 | **3** |
| STOP | 3 | **2** |
| END | 4 | 4 |

A **variant property**, `modern-cmd-encoding`, keeps the classic device's
existing behavior unchanged. Experiment
`experiments/0007-c3-s3-i2c-master.patch` adds the C3/S3 opcode
translation, `I2C_FIFO_ST` at offset `0x14`, IRQ routing through
the chips' interrupt matrix, I2C0 at `0x60013000` on C3, and I2C0/I2C1
at `0x60013000/0x60027000` on S3. It also fixes the off-by-one last
I2C command register decode. No emulated I2C slaves are attached. The
experiment applies **after** the existing ROM patches and experiment
`0006` (ADC) to isolated QEMU; it is not in the standard
`apply_qemu_patches.sh`.

Both compiled QEMU targets passed the **real QTest MMIO contract** using
`probe_i2c_qtest.py`, independent of firmware boot: absent GT911
address `0x5d` NACKs with `raw=0x400` and active IRQ=0x400,
the first command has DONE bit 31, clearing the interrupt works,
RESTART opcode 6 and STOP opcode 2 both set DONE, and the STOP interrupt
sets bit 7 (`0x80`). A 7-second bounded host `timeout` terminates
QTest stdio because QTest has no `quit` command; this is **not** a
guest firmware timeout or an application-boot pass. JSON evidence:
`qa-20261029/c3-i2c-qtest.json` and `qa-20261029/s3-i2c-qtest.json`.
Binary hashes are captured in each report. All 55 Python host
regression tests pass.

Real firmware tests without hardware fake responses:

- **S3 X4 Pro:** transient `qemu_log_mask(LOG_GUEST_ERROR)` instrumentation
  proved the unchanged factory image actually writes I2C0 control
  0x60013004, command registers 0x58=0x3000 (RESTART=6),
  0x5c=0x901 (WRITE one byte with ACK check), 0x60=0x1000 (STOP=2),
  and FIFO_DATA=0xBA (**GT911 address 0x5d in write mode**).
  Its ISR reads status at 0x2c and clears NACK with 0x24=0x400.
  The ESP-IDF 5 driver reports error 259 `ESP_ERR_INVALID_STATE` when
  it receives NACK (its own `esp_driver_i2c/test_apps/i2c_test_apps`
  deliberately checks this return code without an answering slave).
  This is now an **expected missing virtual peripheral**, not proof
  of a broken I2C master. The device itself is not emulated.
  UART `qa-20261029/s3-i2c-mmio-uart.log` and MMIO
  `qa-20261029/s3-i2c-mmio.trace`.
- **C3:** the real factory image again triggered a guest interrupt WDT
  (MEPC `0x4226f5ac`), and the 10-second MMIO trace recorded
  **zero** I2C MMIO accesses before the panic.
  That crash therefore cannot be fixed by simply attaching an I2C
  slave. UART `qa-20261029/c3-i2c-mmio-uart.log`,
  MMIO trace `qa-20261029/c3-i2c-mmio.trace`. Symbolization using

The temporary trace statements were intentionally **reverted**
from the isolated QEMU source and both targets rebuilt afterwards;
they are **not** included in experiment 0007.

**Next real I2C slave requirements** (from the pinned FreeInk SDK
`docs/xteink-x4pro-support.md`): I2C shared bus SDA GPIO39 /
SCL GPIO38; BM8563 RTC (PCF8563 register-compatible) **0x51**,
CW2017 fuel gauge **0x63** with 80-byte BATINFO model and valid

### 29 October (cont.): C3 ADC watchdog hypothesis, strictly experimental

The default ESP32-C3 factory binary `092c2be5` still triggers a
guest `Interrupt wdt timeout on CPU0` at `MEPC=0x4226f5ac` without
I2C MMIO activity when running without `-icount`. The register dump
has S0=`0x60040000`, the C3 APB SARADC MMIO base. A host build of
commit `092c2be5` and pinned FreeInkSDK `44427f8` succeeded
(`pio run -e default -j 2`, incrementally after a time-bounded
first invocation). However, its factory-app IROM segment at
`0x42000020`, length 3,025,832 bytes, matched only
**1,727,687 bytes** of the original image. Do **not** claim
byte-identical ELF symbolization on C3. The guest's nearby machine
instruction bytes are strongly similar, with a two-byte displacement
around the watchdog loop. The rebuilt ELF resolves its analogous
loop to ESP-IDF 5 `adc_oneshot_hal_convert()` /
`adc_oneshot_ll_get_event()`, specifically a read from
`APB_SARADC_INT_RAW_REG` (`0x60040044`) awaiting bit 31 for ADC1.
The guest WDT cause remains an evidence-backed hypothesis rather
than a fully exact-ELF matched identity.

**Experimental QEMU patch 0008**, not part of accepted build
`apply_qemu_patches.sh`, provides a minimal ESP32-C3
ADC oneshot MMIO handshake: select ADC1, assert START in register
`0x60040020` bit 29, report DONE bit 31 at `0x60040044`,
clear DONE via `0x6004004c`. It returns an explicitly dummy zero
raw sample, not real ADC voltage. Isolated QEMU riscv32 rebuilt
successfully. `probe_c3_adc_qtest.py` passed live compiled-QEMU
checks for no premature DONE, proper start/done, dummy zero and
acknowledge clearing. Evidence is
`qa-20261029/c3-adc-qtest.json`.

**Guest result**: a bounded 10s run with 0008 no longer printed
the previous watchdog panic but still did not print normal
application UART output after ROM bootloader entry. A 7s instruction
trace (with `-icount 3`) showed further ROM/IRAM execution, no guest
panic, **not** a successful boot. Evidence:
`qa-20261029/c3-with-adc-uart.log`,
`qa-20261029/c3-adc-patch-trace.log`,
`qa-20261029/c3-adc-patch-trace-uart.log`.
The subsequent stable driver path, timer model, storage and device
readiness need independent verification; an absence of panic in a
bounded run is not acceptance. The C3 ADC sample remains deliberately
inaccurate. Do not ship this prototype as a virtual instrument.

All **58/58 host regression tests pass**. Tests cover simulation
harness and **register contracts**, not complete YBX app startup.

### 29 October: opt-in BM8563 + CW2017 virtual I2C peripherals (experiment 0009)

The pinned FreeInk SDK hardware analysis of Xteink X4 Pro identifies
I2C0 on SDA GPIO39/SCL GPIO38: BM8563 RTC (PCF8563-compatible)
at **0x51**, CW2017 battery fuel gauge at **0x63**, and GT911 touch
at **0x5d**, alternate 0x14. This experiment implements **only**
the RTC and battery; these devices are *simulated*, not sensors on the
user's Mac. The **S3 machine default remains no sensors**, with NACK
for both addresses until explicitly enabled.

A new opt-in parameter is available after applying
`experiments/0009-s3-optin-bm8563-cw2017.patch`
on top of 0007/0008 as documented in the experiments README:

```text
-machine esp32s3,ybx-x4pro-i2c=on
```

Or for the reproducible YBX runner, append `--x4pro-i2c` to an
S3 run with `--s3-octal-psram-mb 8` and the other usual image,
ROM, SD and QEMU root arguments. This flag is forbidden for C3,
explicitly recorded in the boot report as
`virtual_x4pro_i2c_attached`, and **never** sets
`virtual_x4pro_gt911_attached` to true. Unknown I2C addresses
continue to NACK.

- `ybx.bm8563` has the BM8563 register layout: control1/control2
  (0x00/0x01), BCD seconds/minutes/hours/day/weekday/month/year
  (0x02..0x08), and alarm/timer registers through 0x0F.
  It uses QEMU's virtual RTC time offset, supports register-pointer
  writes and repeated-start reads, and deliberately does **not** claim
  full RTC oscillator/alarms/interrupt emulation.
- `ybx.cw2017`: VERSION=0x0D while in normal mode, VCELL at 0x02/0x03,
  SoC at 0x04, MODE=0x08, profile flag=0x0B, 80-byte
  BATINFO registers 0x10..0x5F. Reads show zero percent before
  the profile is uploaded and update-enabled; full 80-byte writes
  followed by the 0x80 flag enable the configurable simulated
  SoC (default **70%**) and simulated VCELL (**3800mV**). This
  is not real battery telemetry. The gauge does **not** infer
  charger state from an I2C register: FreeInk SDK records charging
  on GPIO21, not yet modeled in QEMU. The battery profile bytes
  remain those supplied by the guest (not a copied OEM curve).
- GT911 is **not** attached. It needs GPIO2 active-low power,
  GPIO4 reset and GPIO10 interrupt; QEMU's current
  `esp32_gpio.c` writes are a stub. Adding a slave which always
  ACKs would be demonstrably wrong. Implement GPIO register updates
  and power-gated GT911 behavior first, with tests for NACK while
  unpowered and valid reads only after its reset sequence.

**Verified against actual compiled QEMU**, not a mock: tool
`probe_x4pro_i2c_qtest.py` runs QEMU QTest with the profile
both disabled and enabled, checking real I2C0 MMIO START/STOP,
ACK/NACK, FIFO read, writing/reading the RTC control register,
valid BCD clock, version 0x0D, profile-missing SoC=0,
eight 10-byte BATINFO chunks, full-profile flag, 70% synthetic
SoC, first/last profile byte, and converted simulated 3800mV.
**46 live QTest reads** in the enabled case and **6** in disabled.
Report `qa-20261029/s3-x4pro-rtc-gauge-qtest.json`
includes ROM and QEMU binary SHA256 hashes.

A separate bounded 18-second real-firmware QEMU run using the optional
board profile reached ROM and bootloader entry but did not produce
verified application UART or e-paper/SD mount. This is **not**
an acceptance pass: `qa-20261029/s3-x4pro-rtc-gauge-uart.log`.
Formal runner report is in
`qa-20261029/s3-x4pro-i2c-runner/report.json`.
No synthetic battery or RTC result is presented as real hardware data.

### 29 October: S3 opt-in GPIO output/register groundwork — experiment 0010

The Espressif fork's original `hw/gpio/esp32_gpio.c` ignored all GPIO MMIO writes.
Experiment `0010-s3-optin-gpio-output-registers.patch`, after 0009,
adds the ESP-IDF S3 `GPIO_OUT/OUT1`, `OUT_W1TS/W1TC`,
`ENABLE/ENABLE1`, `ENABLE_W1TS/W1TC` and output-related
input register readback. It introduces 54 named QEMU output lines
`ybx.gpio-pin` to support future GPIO2/4/10 connections.
The legacy behavior remains unchanged unless
`-machine esp32s3,ybx-x4pro-i2c=on` is explicitly selected.
The basic virtual pull-high policy for *unconfigured connected
outputs* is only a board-wiring approximation; this is not full
IO_MUX, pad pull, edge interrupt, or real touch input emulation.

Built Xtensa QEMU successfully. `probe_x4pro_gpio_qtest.py` used
the actual compiled binary, with positive/negative QTest runs,
testing low/high bank bit writes, W1TC, enable masks, readback and
boot strap preservation. Real evidence is in
`qa-20261029/s3-x4pro-gpio-qtest.json`, with binary/ROM SHA256 hashes.
This verifies GPIO **register behavior**, NOT a GPIO-to-GT911
connection. It must not be considered proof of a working touchscreen.

### 29 October: GT911 experiment 0011 — compiled, NOT accepted

`0011-s3-optin-gt911-power-gating.patch` is a draft:
virtual GT911 device with separate S3 machine flag
`-machine esp32s3,ybx-x4pro-i2c=on,ybx-x4pro-gt911=on`.
